## Session: initial scaffolding (2026-07-23)

### Goal
Stand up the project docs (`CLAUDE.md`, `PRD.md`, `progress.md`, `README.md`) and CI/registry plumbing for a new package whose job is to take over the output-loading functionality currently in PhysiCellModelManager.jl (PCMM) at `src/loader.jl`, so loading PhysiCell data no longer drags in the full PCMM dependency. No package code written yet — this session is scaffolding + design lock-in only.

### Source under port
`~/.julia/dev/PhysiCellModelManager/src/loader.jl` (~865 lines). Its real external dependencies are modest:
- **LightXML** — via a small set of navigation helpers (`retrieveElement`, `getSimpleContent`, `getChildByAttribute`, `getChildByChildContent`, `retrieveElementError`, `elementIsTerminal`) that currently live in **ModelManager** at `src/xml_utilities.jl` and are imported by PCMM. We will **copy the minimal subset** into PhysiCellOutput rather than depend on ModelManager — the loader needs only the read-side helpers, none of the variation-file machinery.
- **MAT** — `.mat` reading (`matread`), including the known zero-cell `EOFError` workaround (MAT.jl #240).
- **Graphs / MetaGraphsNext** — the attachment/spring/neighbor `MetaGraph`s.
- **DataFrames**, **Dates** (`Nanosecond`).

The only genuinely PCMM-specific couplings in `loader.jl` are: `assertInitialized()`, `pathToOutputFolder(simulation_id)`, the `Simulation` type, and the `simulation_id::Int` field on the two structs.

### Key decision — identity model (LOCKED)
**Question the user raised:** the `PhysiCellSnapshot`/`PhysiCellSequence` types hold a `simulation_id` that is meaningful only inside PCMM's database. Options:
1. Remove it; key the types on a path.
2. Keep it; have PCMM supply the id and a path resolver (pure "PCMM owns the types" via a field).
2b. (surfaced during discussion) A parametric `source`/`owner` field with a small display interface PCMM implements.

**Chosen: path-based core, PCMM wraps.** PhysiCellOutput types carry `folder::String` (path to the output folder) and **no** `simulation_id`. PCMM converts `simulation_id → path` at its boundary and, where it wants the id shown, wraps the PhysiCellOutput object in a thin PCMM-side struct that adds the id + a custom `show`.

**Why:**
- The standalone package should be meaningful to anyone with a bare output folder; `simulation_id` is noise to them.
- Keeps PhysiCellOutput free of PCMM concepts entirely (no type parameter, no interface to implement) — the simplest possible core.
- The wrapper is cheap for PCMM and keeps PCMM's familiar `SimID=…` display.

**Rejected:**
- *Keep `simulation_id` (pure option 2):* bakes a PCMM-specific integer into a package that otherwise has no notion of it; every user constructing from a folder would have to invent an id.
- *Parametric `source` field (option 2b):* one type, no wrapper, but forces a type parameter through every struct signature and a small display interface onto PhysiCellOutput — more coupling and complexity than the wrapper for no real gain, since PCMM is the only consumer that wants the id.

### API-shape consequences (for the eventual port)
- Struct field `simulation_id::Int` → `folder::String` on both structs.
- Drop `assertInitialized()`, `pathToOutputFolder`, the `Simulation` overloads of `pathToOutputFileBase`/`pathToOutputXML`/`cellLabels`/`cellTypeToNameDict`/`substrateNames`/`cellDataSequence`, and the `simulation_id` overloads of the metadata readers and `cellDataSequence`. PCMM re-adds the id-based overloads in its wrapper layer.
- Keep everything else name-for-name so PCMM's migration is mechanical.
- `show` prints the folder instead of `SimID=`; PCMM's wrapper restores the id in its own `show`.

## Session: remove _safe_matread + write docs (2026-07-23)

### `_safe_matread` removal
The user noted MAT@0.12.1 fixes the zero-column read (MAT.jl #240). Verified against the
installed MAT 0.12.1 by round-tripping empty matrices through `matwrite`/`matread`: both
`(88,0)` and `(0,0)` read back with the correct size and no `EOFError`. Since PhysiCell
writes a zero-cell `cells.mat` as `(nlabels, 0)`, `eachrow` yields `nlabels` empty rows and
`_loadCells!` produces empty typed columns — exactly what the old fallback forced. So
`_safe_matread` is gone; `_loadCells!` calls `matread(mat_file)["cells"]` directly. The
`MAT = "0.12.1"` compat (caret → `[0.12.1, 0.13)`) already floors us at the fixed version, so
no compat change was needed. Tests still 75/75.

### Docs
Built a structured Documenter site mirroring the ModelManager house pattern (a slimmed
version, since this package is small):
- `index.md` — overview, quick start, "where do I look" table.
- `man/installation.md` — registry + add, "what you need" (a folder, not PCMM).
- `man/loading_data.md` — the guide: snapshots vs sequences, lazy vs construction-time
  loading, cells/substrates/mesh/graphs, per-cell time series, PCMM relationship. Its H1 uses
  an explicit `@id loading_data` and its section headers anchor the `index.md` `@ref`s.
- `lib/loader.md` (Public/Private `@autodocs`, `Pages=["/loader.jl"]`), `lib/xml_utilities.md`,
  `lib/index.md` (alphabetical `@index`).
- `make.jl` — `collapselevel=1`, `checkdocs=:exports`, the page tree.

**Doc example blocks use plain ` ```julia ` (non-doctest)** because they need a real output
folder; only the `indexToFilename` jldoctests in the docstrings execute. Built locally clean:
doctests pass, cross-references resolve, `checkdocs=:exports` passes (all exports documented).
Leading `/` on `Pages=["/loader.jl"]` guards against suffix collisions (the ModelManager
`utilities.jl`/`xml_utilities.jl` gotcha), though there's no collision here yet.
